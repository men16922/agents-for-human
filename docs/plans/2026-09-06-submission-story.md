# Rehearsal 제출 초안과 데모 설계

> 2026-09-12 현재 제품은 [실행 전 영향 보고서](../plans/2026-09-12-preflight-impact.md)와 [검증 기록](../test/preflight-impact.md)을 따른다. 아래는 이전 거래 실험/전이 기반의 설계 이력이다.


2026-09-06 · 구현 전 초안. 아직 제출하거나 게시하지 않았다. 공식 요구와 현재 증거의 차이를 유지한다.

## 한 문장과 첫 사용자

**거래 에이전트를 출시하는 개발자가 실패를 재현하고, 실행 정책을 고치고, 다른 상거래 시스템에서 재검증하는 일을 자동화한다.**

영어 피치 초안: “Rehearsal helps developers test transaction agents before delegation. It runs controlled failures, challenges execution plans, and checks whether the revised policy transfers to an independently implemented commerce backend.”

첫 사용자는 구매·결제 도구를 연결하는 개발자와 QA다. 사용자에게 예산·물품·기한을 받고, 평가 사례 작성 → 실행 → 실패 재현 → 수정 비교 → 증빙 정리까지 이어지는 한 업무를 보여준다. 가상의 행사장은 이 업무를 이해시키는 관찰 화면이다.

## 상담을 넘어 무엇을 수행하는가

사용자가 상태를 복사해 설명하지 않아도 도구가 원장을 읽고, 통제된 실패를 실행하며, 반례·정책 버전·재실험을 연결한다. 도구가 연결된 다른 범용 에이전트도 이 일을 할 수 있으므로 “ChatGPT는 불가능하다”고 주장하지 않는다. 차별화 가설은 반복 가능한 거래 환경, 격리된 실험, 독립 상태 검증을 하나의 업무로 제공하는 데 있다.

범용 연결에도 초기 어댑터 작업은 필요하다. POC는 자체 계약과 Medusa 두 환경에 한정한다. SaaS로 확장한다면 같은 commerce API를 쓰는 팀이 어댑터·공통 실패 사례를 재사용하고, 프로젝트별 목표·한도·테스트 자격증명만 설정하도록 만든다. “모든 프로젝트 무설정”은 약속하지 않는다.

## 공식 심사 기준을 증거로 연결

다섯 기준은 동일 비중이다. 자체 예상 점수 대신 각 기준에 보여줄 증거를 준비한다.

| 기준 | 데모에서 보여줄 것 | 개발 후 필요한 증거 |
|---|---|---|
| Technical Implementation | Strands가 실제 계획·도구 실행·반례 검토를 수행 | 모델 도구 호출 trace, 비용, 복구, 독립 API 결과 |
| Design | 목표 입력부터 결과 확인까지 하나의 흐름 | 상태 신선도·지급/수령 분리·실패와 중단 UX |
| Potential Impact | 개발자의 반복 검증 업무와 그 산출물 | 가능하면 2~3명 관찰, 없으면 효용 가설 명시 |
| Creativity & Originality | 반복 리허설이 정책을 바꾸고 외부 재검증으로 이어짐 | 반례 → 정책 diff → 미공개/E2 결과 연결 |
| Presentation | 한 임무의 변화·복구·검증을 이해할 수 있게 구성 | 5분 이내 영어 영상, 재현 절차, 아키텍처 그림 |

공식 규칙은 작동하는 공개 데모 또는 AgentCore 배포가 기술 점수를 강화한다고 설명한다. 핵심 기능 검증 후 제출 선택지로 검토한다. Builder Center 글은 건당 0.2, 최대 0.6 보너스가 안내되어 있다. 실제 AWS 구현 후 ‘문제와 설계’, ‘Strands 실행·검토’, ‘평가 결과·한계’로 나눠 작성할 수 있으나 게시되지 않은 초안은 가점 완료가 아니다. [공식 규칙](https://agentsforhumans.devpost.com/rules).

## 4분 45초 데모 구성

| 시간 | 장면 | 반드시 실제 실행으로 보여줄 것 |
|---|---|---|
| 0:00–0:25 | 개발자가 반복 검증해야 하는 이유 | 재고 변화·지급 응답 유실이라는 구체적 문제 |
| 0:25–0:55 | 행사 준비 임무 입력 | 텐트 3, 조명 6, 예산 500, 기한과 완료 조건 |
| 0:55–1:45 | 리허설과 Peer Review | 실패 로그·검토자의 반례·정책 변경 |
| 1:45–2:40 | 계속 움직이는 운영형 세계 | 실제 재고 이벤트, 오래된 계획 재검토, 대체 조달 |
| 2:40–3:35 | 응답 유실과 복구 | 지급 미확정, 동일 intent 조회, 수령 후 완료 |
| 3:35–4:15 | 독립 Medusa 결과와 비교 | 자체 화면과 외부 주문·원장 증거 대조, 실패 포함 분모 |
| 4:15–4:45 | 실제 가치와 적용 범위 | 비용·개입·한계, 재현 경로, 남은 과제 |

AI 생성 이미지와 현재 HTML 장면은 설계 설명에만 사용한다. 구현 영상에 넣을 때 작동 중인 제품 화면처럼 편집하지 않는다. 전체 실행이 5분을 넘으면 시간 압축임을 표시하고 원본 로그·시간을 함께 제공한다. 외부 전이가 실패했다면 실패와 원인을 보여주고 E1 달성 범위로 표현한다.

## 현재 고정한 범위와 보류한 확장

- 유지: Strands 실제 업무 수행, 작은 2D 거래 세계, 실시간 반영, 정책 동결, B0~B3 비교, 독립 검증기, E2 목표.
- 보류: 실제 자금·스테이블코인, A2A 서비스 분리, 다수 동시 사용자, 3D 게임, 자동 환급, 결제 사업 출시.
- 첫 개발 검증: 이미 기동한 Medusa에서 고객/판매자 권한을 나누고 실제 주문·지급·fulfillment 상태 계약을 수집한다(CW00).
- 제출 전: 영어 설명·테스트 절차·영상, 공개 저장소의 MIT/Apache 파일과 제3자 고지, 아키텍처, Builder ID, 무료 심사 접근을 확인한다. 공개·배포·게시·제출은 아직 수행하지 않았다.
