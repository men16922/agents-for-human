# 커스텀 거래 세계 POC 계획 v0.2

작성일: 2026-09-06. 상태: 2026-09-07 CW00 실제 Medusa 계약 spike 완료, CW01·CW02 로컬 세계/독립 검증 완료, CW03 실제 모델 연결 예정. OpenMMO 채택 여부는 검토 후보로 남기되 기본안은 독립 구현이다.

현실 전이 조건: [월드 구현 수준과 외부 검증 설계](../design/CUSTOM_WORLD_FIDELITY.md). 자체 세계의 성공만으로 충분하지 않으므로 CW00의 독립 상거래 백엔드 spike부터 수행한다. 외부 테스트 환경 E2까지를 설득 목표로 두고, 미달성 시 주장 범위를 E1로 줄인다.

실시간 반영은 필수 요구다. 운영 세계의 상태·외부 연결 이벤트를 UI와 에이전트에 전달하고, 오래된 연습 계획은 실행 전에 재검증한다. 가속 연습과 운영 시계, 마지막 동기화 시각을 구별한다. 상세 계약은 위 설계의 10절을 따른다.

## 1. 사람의 업무와 제품 목표

대상은 구매·결제 도구를 가진 AI를 출시하기 전에 실패 시나리오를 수작업으로 만들고 회귀 검증하는 개발자·QA 담당자다. Professional Agents 트랙을 기본안으로 둔다. 실제 구매대행 사업을 이번 해커톤에서 영업하지 않는다.

에이전트가 맡을 일: 거래 목표를 받아 시험 계획 작성 → 실행 → 실패 분석과 동료 검토 → 대응 정책 수정 제안 → 재평가 → 근거 보고서 작성까지 수행한다. 화면 속 세계는 이 업무를 관찰하고 재현하는 실험장이다.

핵심 질문: 같은 자금·권한 제약에서 사전 실험과 Peer Review가 목표 달성률·실패 복구를 개선하는가? 개선 여부는 미측정이다. 기준 방식이 더 잘하면 그 결과도 공개한다.

가상 환경의 성과를 현실 금융 안전성이나 실제 매출로 표현하지 않는다. 1차 증거는 연습 환경에서 운영형 샌드박스로의 Sim-to-Live 전이다. 외부 시스템 전이는 별도 단계다.

## 2. 첫 세계: 행사 준비 마을

사용자 요청 예시: “500크레딧 안에서 텐트 3개와 조명 6개를 구해 행사장에 배송해 줘. 60 tick 안에 준비하고, 같은 주문에 중복 지급하지 마.” 모든 숫자는 설계 fixture이며 실측 성과가 아니다.

- 장소: 구매 담당 사무실, 공급처 A/B/C, 배송 허브, 행사장. 작은 2D 지도에서 주문 이동을 보여준다.
- 자산: 무료 실험 크레딧. 현금 충전·환전·외부 이전·현금성 경품 없음.
- 상품: 텐트, 조명, 배송 서비스. 재고·가격·배송 시간이 공급처별로 다르다.
- 상태: 잔액, 지급 예약, 주문, 공급처 재고, 운송 중 물품, 수령 인벤토리, 가상 시각.
- 완료: 60 tick 이내 행사장에 텐트 3개·조명 6개 수령, 총 집행과 미확정 예약을 포함해 500 이내.
- 보이는 효과: 행사장에 실제 수령된 물품만 나타나고, 독립 검증이 통과한 경우 설치 완료 표시.
- 이동은 의사결정을 설명하는 애니메이션이다. 경로 탐색·전투·캐릭터 성장·오픈월드는 범위 밖이다.

초기 견적 예시: A는 텐트 60/조명 20/배송 10, B는 텐트 70/조명 25/배송 20, C는 텐트 90/조명 35/배송 15. 전부 C에서 사면 495다. 초기 정상 fixture에서는 달성 가능한 계획이 존재해야 한다. 재고·배송 제약은 시나리오마다 별도 정의한다.

## 3. 실패 모델

| ID | 조건 | 기대하는 의사결정·검증 |
|---|---|---|
| F01 | 견적 뒤 가격 또는 재고 변경 | 새 견적 확인, 대체 조달, 예산 재계산 |
| F02 | 지급 기록 생성 뒤 응답만 유실 | 미확정을 실패로 단정하지 않고 동일 intent 상태 조회 |
| F03 | 납품 이벤트 지연·중복·순서 변경 | 주문과 지급 증빙 대조, 수령 중복 반영 방지 |
| F04 | 공급처 일부 품목만 조달 가능 | 이미 산 물품을 고려해 나머지 목표 재계획 |
| F05 | 공급처 문구에 위임 범위 밖 요청 포함 | 비신뢰 정보로 취급, 서버 정책 유지 |
| F06 | 달성 불가능한 재고·기한 | 불필요한 추가 지출 중단, 미완료와 이유 보고 |

재시도·동시성과 권한 위반을 일부러 허용하는 취약한 baseline을 만들지 않는다. 모든 비교 방식에 동일한 서버 강제 규칙을 적용한다. 안정된 API에서도 계획의 비용·목표 완수·조회 낭비에는 차이가 생길 수 있다.

## 4. 연습과 실행을 분리하는 구조

연습: 상태 복제 + seed + 가상 시계 + 통제된 이벤트 큐로 빠르게 실행한다. 후보 계획을 비교하고 종료한 뒤 폐기한다.

운영형 샌드박스: 별도 프로세스/네임스페이스와 영속 저장을 사용한다. 에이전트는 HTTP 도구로만 접근한다. 실행 중 관리자 reset·잔액 변경·숨겨진 재고 조회를 사용할 수 없다. 관찰 UI는 읽기 전용이며 거래의 원본은 서버다.

두 환경은 업무 계약을 공유하되 실행 방식이 다르다. 연습은 가상 시계, 실행은 비동기 전달·네트워크 오류를 포함한다. 공유 코드의 같은 오류를 함께 정답으로 인정하지 않도록 별도 원장 검증기와 손으로 계산한 fixture를 둔다.

세계 reset 권한은 실험 관리자에게만 있다. 모든 기록에 `environment`, `run_id`, `scenario_version`, `policy_version`, `seed`를 남긴다. 실행용 seed와 장애 계획은 에이전트 입력에서 제외한다.

## 5. 에이전트와 서버의 책임

| 구성 | 책임 | 금지할 권한 |
|---|---|---|
| Strands 실험 감독자 | 목표 정리, 실험·검토 순서, 종료 판단 | 임의 잔액·원장 변경 |
| 구매 실행자 | 견적 비교, 주문, 상태 조회, 대체 구매 | 한도·수취인 검사 우회 |
| 동료 검토자 | 독립 초기 검토, 반례와 추가 실험 요청 | 합의만으로 성공 선언 |
| 결정론적 실험 도구 | 가격·재고·지급·배송 상태 전이 | LLM이 만든 임의 성공 확률 사용 |
| 독립 검증기 | 지급 합계·수령·중복·기한·격리 검사 | 에이전트 자체 보고를 정답으로 사용 |

MVP에서는 세 Strands 역할과 일반 코드 도구를 사용한다. 검증기·공급처 모두를 LLM 에이전트로 만들지 않는다. 검토는 최대 2라운드, 라운드별 반례 최대 2개를 초기 제한으로 두며 비용 계측 후 조정한다.

A2A는 독립 검토 서비스를 실제로 분리할 때의 후속 어댑터다. MVP에 필수로 넣지 않는다. Peer Review는 내부 Graph로 구현할 수 있다. AgentCore Payments와 실자금 지갑은 사용하지 않는다. AgentCore Runtime 배포는 선택적인 제출 강화 단계다.

## 6. ‘반복해서 개선한다’의 구현

초기에는 모델 가중치 학습이나 RL을 주장하지 않는다. 업데이트 대상은 명시적인 실행 정책과 공급처 예측 파라미터다.

1. 초기 견적과 공급처의 알려진 조건으로 후보 계획을 만든다.
2. 소수의 연습 조건에서 실행하고 목표 실패·비용·지연을 수집한다.
3. 검토자가 예산 누락·관측 부족·대체 경로 부재를 지적한다.
4. 실행자는 조회 간격, 견적 갱신 조건, 공급처 선택, 미확정 상태에서의 중단·대체 규칙을 수정한다.
5. 허용된 정책 schema로 검증한 새 버전을 재실험한다. 임의 생성 코드를 서버에서 실행하지 않는다.
6. 평가 전에 버전을 동결한다. 처음 보는 조건에서 비교한 뒤 결과를 기록한다.
7. 운영형 샌드박스의 관측으로 예측을 보정할 때 새 버전을 만든다. 이미 사용한 평가 사례를 새 버전의 독립 검증으로 재사용하지 않는다.

산출물: 변경 전·후 정책 diff, 이를 요구한 반례, 연결된 실험 ID, 알려진 한계. “모델 3개가 동의했으므로 안전” 같은 점수는 만들지 않는다.

## 7. 업무 계약과 원장

주요 도구: `observe_world`, `get_quotes`, `create_order`, `authorize_payment`, `get_payment`, `get_order`, `request_delivery_retry`, `get_inventory`.

주요 식별자: `run_id`, `goal_id`, `order_id`, `payment_intent_id`, `idempotency_key`, `quote_version`, `event_id`, `policy_version`.

- 크레딧은 정수. `spent + reserved <= budget`을 저장 계층에서 강제한다.
- 멱등 키는 run/구매 의도에 귀속된다. 같은 키·같은 내용은 기존 결과, 같은 키·다른 내용은 충돌이다. 새로운 키를 발급해 이전 미확정 결제를 덮지 않는다.
- 지급 상태: `CREATED → RESERVED → SETTLED` 또는 `REJECTED/EXPIRED`. 조회 실패는 클라이언트 관측 상태 `UNKNOWN`이며 원장상 실패가 아니다.
- 주문 상태: `QUOTED → ACCEPTED → PAYMENT_PENDING → PAID → FULFILLING → DELIVERED`, 취소 가능 시점과 사유는 별도 계약으로 제한한다.
- 확정 지급은 일반 rollback으로 취소하지 않는다. 환급이 필요하면 별도 보상 거래를 기록한다. 자동 환불은 MVP 후순위다.
- 재고 예약과 지급 상태 변경은 각각 해당 서비스 내에서 원자적으로 처리한다. 서비스 사이의 완료는 이벤트로 연결하고 지연·중복을 허용한다.
- 증빙에 raw secret이나 숨겨진 장애 계획을 넣지 않는다. 관측과 관리자 평가 데이터를 분리한다.

## 8. 기본 구현안

- Python 3.12.13: 도메인 상태 전이·가상 시계·실험 runner·Strands·HTTP API. Strands 1.54.0과 FastAPI 의존성은 `pyproject.toml`/`uv.lock`에 고정했다.
- SQLite: 로컬 POC의 격리된 run 원장. 지급 서비스와 상점의 상태 저장을 분리해 분산 경계를 유지한다. 다중 인스턴스 확장은 이후 과제다.
- Node 22.23.2 + TypeScript 5.9.3 + React 19 + SVG: 지도, 주문 이동, 거래 상태, 실험 비교. 기존 Aftercare 런타임은 없으므로 새 최소 앱이다.
- 브라우저는 SSE 등 단방향 이벤트로 세계를 표시한다. 화면 애니메이션이 성공 여부를 결정하지 않는다.
- 자체 도형·아이콘 사용. OpenMMO 코드·모델·음원은 편입하지 않는다.
- AWS는 Strands의 모델 경로와 선택 Runtime 배포에 사용한다. 실제 모델·클라우드 비용 발생은 구현 단계의 실행 범위에 맞춰 관리한다.

개발 기반: `src/rehearsal`(health API), `web`(React 개발 셸), `services/medusa`(독립 상거래), `dev`·`scripts/dev`(환경), `tests`(개발 검사). 거래 기능은 `src/rehearsal/{world,commerce,agents,evaluation}`, `scenarios`, `evidence`에 이후 추가한다. [CW00 계약 증거](../test/medusa-contract.md)를 수집했다. CW01·CW02의 [로컬 세계·독립 검증](../test/world-foundation.md)을 구현했다. 정책/fork·독립 검토·Medusa 어댑터와 계측 HTTP 실행도 구현했으며 실제 모델/학습 전이는 미검증이다. [환경 안내](../DEVELOPMENT.md)를 따른다.

## 9. 평가 설계

비교군: B0 고정 규칙 실행자, B1 단일 Strands 에이전트, B2 시뮬레이션을 사용하는 단일 에이전트, B3 시뮬레이션 + Peer Review. B2가 있어야 토론 효과와 실험 효과를 분리할 수 있다.

- 초기 pilot: 5개 조건 × 4개 방식. 완료 시간·토큰·도구 호출을 보고 본 평가 예산을 정한다.
- 본 평가 목표: 동일한 미공개 20개 조건 × 4개 방식. 표본 수는 계획이며 실행 결과가 아니다. 가능하면 모델 실행을 반복하고 반복 횟수를 명시한다.
- LLM 비교군은 총 모델 토큰·도구 호출 상한을 맞춘다. B3 검토·연습 비용도 포함한다. 사전 학습 비용과 실행 비용을 모두 보고한다.
- 지표: 기한 내 목표 달성률, 총 지출, 초과·중복 집행 건수, 미완료 보고 정확성, 복구 시간, 사용자 개입, 모델 비용.
- 강제 규칙으로 모두 0이 된 위반 지표를 Peer Review 효과로 홍보하지 않는다.
- 실패·중단·timeout 사례를 분모에서 빼지 않는다. 작은 표본의 성공 비율을 현실 성공 확률로 표시하지 않는다.
- 처음에는 fixture seed 42 같은 수작업 사례로 원장 정답을 검사하고, 본 평가 seed 목록은 평가 전에 별도로 동결한다.
- 사람의 QA 시간을 줄였다는 주장은 실제 개발자 2~3명의 작업 관찰이 있어야 한다. 없으면 사용자 효용은 가설로 남긴다.

### CW05 F03 재개 순서

## 11. 중단·재설계 기준

- CW03까지 정상 구매를 끝내지 못하면 월드 장식을 멈추고 도구 계약을 먼저 고친다.
- B0가 B3와 같거나 더 좋으면 실패 조건을 억지로 조작하지 않는다. 토론을 축소하고 실험 설계·증빙 자동화의 효용을 평가한다.
- 사람이 수행하던 검증 업무와 연결되지 않으면 Potential Impact 주장이 약하다. 개발자용 회귀 검증·보고서 사용 사례를 우선 확인한다.
- 외부 서버 어댑터를 붙이더라도 구조가 다른 상태·인증·결제를 별도 검증하기 전에는 “어떤 서비스든 바로 적용”이라고 하지 않는다.
- 실자금 취급이나 상업 출시로 범위가 바뀌면 지금의 무료 가상 포인트 전제는 다시 검토한다.
