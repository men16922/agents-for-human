# 커스텀 월드의 구현 수준과 현실 전이 검증

> 2026-09-12 현재 제품은 [실행 전 영향 보고서](../plans/2026-09-12-preflight-impact.md)와 [검증 기록](../test/preflight-impact.md)을 따른다. 아래는 이전 거래 실험/전이 기반의 설계 이력이다.


2026-09-06 · 거래 기능 설계. 2026-09-07 [CW00 실제 거래 계약](../test/medusa-contract.md)을 확인했다. [CW01·CW02 로컬 세계/독립 검증](../test/world-foundation.md)도 구현했다. 아래 모델·실시간 운영·전이 기능과 성과는 아직 구현·측정하지 않았다.

## 1. 무엇에 대한 확신을 줄 것인가

자체 가상 세계에서 성공했다는 사실만으로 현실 구매·송금의 안전을 보장할 수 없다. 이번 POC가 줄 수 있는 근거는 범위가 한정된 거래 목표와 실패 조건에서 실행 전략이 다른 시스템으로 전이되는지에 대한 관측이다.

최소 설득 기준: **우리 시뮬레이터에서 개선한 정책을 동결하고, 우리가 구현하지 않은 상거래 백엔드에서도 목표를 완수하며, 원장·주문 상태로 이를 독립 확인한다.** 외부 환경에서 실패한 뒤 정책을 고쳤다면 그것은 적응 결과이며 최초 전이 성공으로 기록하지 않는다.

자체 월드만 구현되면 “거래 에이전트 평가 샌드박스”라고 소개한다. 외부 상거래 API까지 검증하면 해당 계약과 조건에 한정해 “외부 상거래 환경 전이 POC”라고 소개한다. 실자금 운영·법적 적합성·전체 실패 확률은 별도 검증 대상이다.

## 2. 화면 수준: 작은 2D 운영 지도

지도는 사무실 → 공급처 2~3곳 → 배송 허브 → 행사장으로 구성한다. 실제 상거래 상태가 바뀔 때 해당 장소·주문 카드·배송선이 변한다. 멋진 지형보다 사용자가 원인과 결과를 읽을 수 있는 화면이 우선이다.

| 영역 | 보여줄 내용 | 구현 수준 |
|---|---|---|
| 상단 목표 | 필요한 물품, 예산, 기한 | 실제 goal 데이터 |
| 중앙 지도 | 공급처, 재고, 운송, 수령 장소 | SVG 도형과 간단한 이동·색 변화 |
| 좌측 계획 | 선택한 공급처와 변경 이유, 미확인 조건 | 구조화된 계획·근거 요약 |
| 우측 거래 | 주문·지급·배송의 서로 다른 상태 | 서버 이벤트에서 표시 |
| 하단 실험 | 초기 정책/수정 정책, 조건, 실패·복구, 비용 | 실제 실행 이력과 버전 |
| 상세 증빙 | 요청 ID, 주문 ID, 지급 ID, 원장 대조 | 클릭해서 확인·내보내기 |

한 세션은 목표 1개·물품 2종·공급처 최대 3곳·구매 실행자 1개·검토자 1개부터 시작한다. 수백 명 NPC·전투·물리 엔진·3D 캐릭터·자유 건축은 필요하지 않다. 사용자에게 게임 규칙을 학습시키지 않는다.

## 3. 현실성과 직접 관련된 다섯 가지

### 업무 계약

상품 조회, 견적 유효기간, 주문 생성, 지급 요청, 지급 상태 조회, 납품 확인을 분리한다. 각 필드와 상태는 목표 외부 백엔드의 문서·실제 응답에 대응시킨다. 만들기 쉬운 가상 API를 먼저 확정하고 외부 시스템을 억지로 맞추지 않는다.

### 비동기 상태

주문 생성 성공 ≠ 지급 확정 ≠ 납품 완료. 응답 유실은 지급 실패가 아니다. 조회 오류와 원장 결과를 별도로 기록한다. 수령 UI는 지급 응답만으로 완료되지 않는다.

### 권한과 관측

에이전트에는 고객이 실제로 볼 수 있는 API만 준다. DB 직접 읽기, 관리자 지급 완료 설정, 다음 장애 시각, 숨겨진 재고를 주지 않는다. 검증기·장애 주입자는 별도 자격을 쓰며 에이전트와 정보를 공유하지 않는다.

### 실패 경계

지급 처리 뒤 응답 유실, webhook 중복·지연, 재고 경합, 견적 만료를 HTTP 경계에서 주입한다. 외부 제공자의 공유 인프라에 장애나 부하를 주지 않는다. 우리 테스트 proxy에서 자신의 요청·응답을 지연·유실시키는 방식이다.

### 규칙의 충실도

멱등성, 예약 잔액, 주문 상태 전이, 취소 가능한 시점은 특정 외부 서비스와 대조한다. 시간·요금·재고의 분포를 실제 관측하지 않았다면 “합성 조건”으로 표시한다. 전체 현실 분포를 대표한다고 하지 않는다.

## 4. 증거를 쌓는 단계

| 단계 | 환경 | 증명할 수 있는 것 | 증명하지 못하는 것 |
|---|---|---|---|
| E0 | 자체 시뮬레이터, 알려진 사례 | 규칙·도구·원장 동작 | 새로운 조건의 성능 |
| E1 | 숨긴 seed·조합의 자체 월드 | 정의한 실패 공간 안의 일반화 | 다른 구현으로의 전이 |
| E2 | 별도 상거래 백엔드의 테스트 인스턴스 | 외부 주문·재고·납품 계약에서의 전이 | 실제 결제망·현금 정산 |
| E3 | 외부 결제 제공자의 정식 sandbox | 해당 제공자의 테스트 거래·이벤트 처리 | 실제 고객·사기·분쟁·운영 규모 |
| E4 | 적법하고 승인된 제한적 실운영 | 그 조건에서 관측한 실제 거래 결과 | 모든 환경의 안전·성공 보장 |

이번 계획의 설득 목표는 E2다. E3는 제공자 계정·지원 결제 수단·일정이 확인되면 추가한다. E4는 이번 범위에 넣지 않는다. E2를 못 만들면 E1까지만 달성했다고 명시한다.

## 5. 외부 환경 후보: Medusa core

Medusa는 주문·재고·결제·fulfillment를 다루는 상거래 플랫폼이다. 문서에 payment session, 승인과 지연 승인 같은 흐름이 정의되어 있어 외부 계약의 후보가 된다. core는 MIT이며 별도 Enterprise 영역은 상용 조건이다. 이번 후보는 core에 한정한다. Medusa 2.20.1 설치·DB 마이그레이션·health HTTP 200은 확인했다. RBAC는 비활성화하며, 주문·지급·납품 API의 의미는 CW00에서 실측했고 전이 효과는 CW05 이후 검증한다.

E2 spike는 자체 설치한 독립 Medusa core에서 테스트 카탈로그·장바구니·주문·재고·fulfillment 경로를 확인한다. 수동/테스트 지급 제공자를 쓴다면 실자금 결제 검증이 아님을 표시한다. 에이전트의 구매 권한과 판매자의 납품 권한을 분리한다. 별도 상점 프로세스가 허용된 관리자 작업을 수행하며, 구매 에이전트에게 관리자 토큰을 주지 않는다.

E3 후보로 Stripe sandbox가 있지만 자동 채택하지 않는다. 카드 테스트 흐름을 사용했다면 스테이블코인 정산을 검증했다고 말할 수 없다. 스테이블코인이 후속 핵심이면 해당 토큰·네트워크·제공자의 공식 테스트 경로를 따로 확인한다.

## 6. 어댑터가 답을 대신 풀지 않도록 하는 원칙

- 정책·프롬프트·모델·도구 의미·지출 규칙을 평가 전에 동결한다.
- 어댑터의 역할은 인증, 필드와 상태 매핑, 프로토콜 전달이다. 외부 환경에서만 자동 복구·대체 구매·추가 정답 정보를 제공하면 안 된다.
- 두 환경의 상태 전이 대조표를 작성하고 정상·거절·미확정 사례를 각각 확인한다.
- 운영형 환경에만 필요한 차이는 기록하고, 구현 독립성과 의미 차이를 구별한다.
- 모델에는 자신의 거래 응답만 보이고, 평가자는 별도 API·원장·DB의 권한 있는 읽기로 정답을 검사한다.

## 7. 가상 세계가 현실을 잘못 가르치는지 먼저 검사

외부 백엔드와 시뮬레이터에 같은 합법적인 작업 순서를 보내고 중요한 관측을 비교한다. 단순 문자열 일치 대신 “지급은 미확정, 재시도는 동일 intent, 주문은 미배송” 같은 의미를 비교한다.

예: 주문 → 지급 → 응답 유실 → 지급 재조회 → 주문 조회 → 납품. 두 환경 중 한쪽만 재조회가 가능한 경우 이를 지원 차이로 기록한다. 시뮬레이터에서만 가능한 마법 같은 복구 API를 실제 전이 결과에 사용하지 않는다.

차이가 발견되면 시뮬레이터 또는 어댑터를 수정하고 검증 사례를 추가한다. 수정에 사용한 사례는 이후 최종 평가용 새 사례와 분리한다. 정답 검증기는 서버 구현을 그대로 호출해서 스스로를 채점하지 않는다.

## 8. 평가와 주장

E1은 실행 계획의 비교, E2는 전이 여부의 확인으로 분리한다. E1 비교는 POC 계획의 B0~B3를 따른다. E2는 같은 초기 상태에서 B1과 B3를 우선 비교해 비용을 제한한다. 모델 비결정성·관측 지연·실패 사례·횟수를 모두 남긴다.

평가표의 필수 열: 환경, 정책 버전, 사례, 목표 완료, 집행/예약 금액, 중복 지급, 수령 수량, 사용자 개입, 모델·도구 비용, 실패 원인.

20개 사례에서 성공한 비율은 “평가 사례 성공 비율”이다. 현실 성공 확률 95%처럼 바꾸지 않는다. 모두 성공해도 관측하지 않은 실패를 부정할 수 없다. 정책 위반이 서버에서 막혔다면 그 성과는 서버 제약에 귀속하고 토론 효과로 표시하지 않는다.

발표 문장 예시: “합성 거래 조건에서 개선한 정책을 동결하고 별도 상거래 백엔드의 테스트 환경으로 옮겼습니다. 평가한 N건에서 목표 완료·지출·수령을 독립 확인했습니다. 실제 자금 정산은 검증 범위에 포함하지 않습니다.” N과 성과는 측정한 뒤 채운다.

## 9. 일정 변경: 외부 연결을 먼저 확인

CW00을 가장 먼저 수행한다. 한 작업일을 조사·기술 spike의 제안 상한으로 두고 Medusa core의 최소 주문 흐름과 필요한 테스트 권한을 확인한다. 라이선스가 확인된 버전을 고정하고, 실행에 필요한 자원·설정·문제를 기록한다.

CW00 결과를 기준으로 거래 계약을 정한 뒤 CW01의 자체 월드를 만든다. E2 adapter 구현은 UI보다 앞에 둔다. 외부 전이가 기술적으로 막히면 장식을 늘리지 말고 다른 독립 백엔드를 검토하거나 E1 평가 도구로 주장 범위를 줄인다.

## 10. 실시간 반영 요구사항

사용자 요구: 시뮬레이션은 최소한 실시간으로 반영되어야 한다. 기본 해석은 운영형 세계의 실제 상태 변화를 UI와 에이전트가 연속적으로 관측하는 것이며, 외부 백엔드 연결 시 그 이벤트도 같은 경로로 반영한다. 현실의 모든 가격·재고를 자동 수집한다는 뜻은 아니다.

### 두 시계와 실제 상태

- 운영형 세계: 서버 시계 기준 1 tick = 1초를 초기안으로 두고 계속 진행한다. LLM 응답을 기다리느라 세계 전체가 정지하지 않는다. 요청·외부 이벤트는 도착한 시점에 처리하며 tick까지 반드시 지연할 필요는 없다.
- 연습 세계: 특정 시점의 상태와 관측 버전을 복제하고 가상 시계로 빠르게 반복한다. 화면에 “가속 연습”과 시작 snapshot 시각을 표시한다. 이 실행은 운영 원장에 영향을 주지 않는다.
- 가격·재고·잔액은 서버에서 변경되며 화면은 그 결과를 반영한다. 임의 애니메이션으로 실제 완료를 앞서 표시하지 않는다.
- 본 계획의 60 tick 기한은 운영형에서는 초기안 기준 60초다. 모델 지연 pilot에서 현실적인 기한으로 조정한 뒤 평가 전에 고정하고 비교군 모두에 동일하게 적용한다.

### 이벤트 전달과 신선도

서버/외부 connector → 상태·원장 변경과 내구성 있는 이벤트 기록 → UI 스트림 및 에이전트 관측 큐 순서로 구성한다. SQLite 단일 서비스에서는 상태와 outbox를 같은 transaction에 기록하고, 서비스 간에는 중복 가능한 이벤트 전달을 전제로 한다.

이벤트 필드: `event_id`, `run_id`, `source`, `aggregate_id`, `aggregate_version`, `occurred_at`, `received_at`, `event_type`, `payload`. 외부 제공자가 순서를 보장하지 않으면 수신 순서를 사실 순서로 간주하지 않고 현재 상태를 재조회한다. 전역 완전 순서를 가정하지 않는다.

- 가격 변경, 재고 예약/소진, 지급 미확정/확정, 납품 지연/완료를 UI에 SSE로 전달하는 방식을 기본안으로 둔다.
- 재접속은 마지막 이벤트 cursor 이후를 복구한다. 보관 범위 밖이면 새 snapshot과 cursor를 받는다. 중복 이벤트는 ID/버전으로 제거한다.
- 공급처 정보에는 마지막 확인 시각과 stale 상태를 표시한다. 외부 webhook이 없으면 허용된 polling 주기를 표시하며 “즉시 동기화”라고 하지 않는다.
- 초기 UI 목표는 내부 이벤트 발생부터 화면 반영까지 p95 1초 이내다. 설계 목표이며 측정 전 성과로 쓰지 않는다. 외부 전달 지연과 LLM 판단 시간은 따로 측정한다.

### 에이전트가 변화에 대응하는 방법

새 관측은 모두 기록하되, 계획에 영향을 주는 재고·견적·지급 변화에서만 재판단을 요청한다. 비관련 이벤트와 반복 알림은 합친다. LLM을 프레임이나 tick마다 호출하지 않는다. 실행자가 처리 중이면 관측 버전을 갱신하고, 부작용 실행 직전에 최신 조건을 확인한다.

연습 계획은 `based_on_snapshot`, `quote_version`, `expires_at`에 연결한다. 운영 세계가 달라지면 계획을 그대로 집행하지 않는다. 단순 재조회로 확인 가능한 변화는 재조회하고, 경로·예산이 달라지는 변화는 남은 목표를 재계획한다. 최종 재고·한도 검사는 서버 transaction이 수행하므로 사전 조회만으로 경합을 방지했다고 하지 않는다.

데모: 연습 중 다른 참여자가 A상점 재고를 소진 → 화면과 실행자에 이벤트 도착 → 이전 계획이 오래되었다고 표시 → B상점 견적 확인 → 남은 예산 안에서 재계획 → 실제 운영 원장에서 구매·수령 확인. 가격 변동을 연출용 텍스트만 바꾸는 방식으로 만들지 않는다.

검증: 두 브라우저에서 같은 상태, 재접속 후 누락 복구, 중복/역순 이벤트, 연습 중 운영 재고 변경, LLM 지연 중 세계 진행, 오래된 견적 거절, run 간 이벤트 격리를 확인한다. 외부 상태를 반영하는 E2에서는 공급처 API의 실제 변경으로 이 흐름을 다시 검증한다.
