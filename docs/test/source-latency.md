# CW06 — 재고 변경 구간과 실제 화면 반영 연결

2026-09-09. 기존 지연 표본의 시작점을 감사하고, 실제 Medusa 재고 변경 20건을 화면 반영과 새로 연결했다. 별도 gate가 겹친 최초 20건도 보존했다. **깨끗한 두 번째 실행의 변경→화면 p95는 로컬 시계 비교를 전제로 1,275~1,316ms 범위다.** 이는 요청 구간으로 구한 발생 시각의 범위이며 신뢰구간이나 전체 성능 목표의 판정이 아니다.

## 기존 자료로 측정할 수 없었던 구간

[기존 원시 자료](../../evidence/cw06-latency/browser/latency.json)의 24건을 [영속 시각](../../evidence/cw06-latency/timing-source.json)과 다시 대조했다. 9개 보존 파일의 hash와 event ID/version/cursor/시각이 일치했다. 반영 22건은 첫 관측 1·시계 갱신 19·상태 변화 2이며, 지연 납품 2건은 old/duplicate로 미반영됐다. 독립 재계산은 관측→반영 p95 966.184ms, 조회 시작→반영 p95 1,028.379ms로 이전 기록과 일치했다.

`Observer.poll()`은 외부 조회 **완료 후** `observed_at`을 만든다. `poll_started_at`은 조회를 시작한 시각이며 외부 상태 변경 시각이 아니다. 자체 원장의 `occurred_tick`도 정확한 wall-clock 발생 시각을 제공하지 않는다. 따라서 이 자료만으로 설계의 내부 이벤트 발생→화면 반영 목표를 계산할 수 없다. [감사 JSON](../../evidence/cw06-source-latency/retained-sample-audit.json)에 계산과 분모를 남겼다.

## 추가한 측정

`make commerce`가 준비된 상태에서 `make commerce-latency-smoke`를 실행한다. [Python driver](../../scripts/commerce/latency_smoke.py)와 [브라우저 probe](../../scripts/commerce/latency_browser.mjs)는 다음 순서로 검사한다.

1. 20개 명부와 순서·대기 간격을 변경 전에 저장한다. 초기 A 텐트 재고 10에서 1~20으로 순차 변경한다. 각 값이 확인된 뒤 다음 요청을 시작하는 알려진 순차 부하다.
2. 실제 페이지의 DOM 관측기를 먼저 준비한다. 독립 운영자 경로로 이 실행의 Medusa 재고만 수정하고, 호출 전/후 epoch와 monotonic 시각·실제 변경 전/후 응답을 보존한다. 해당 helper에는 사전 조회·수정·확인 조회가 모두 포함된다.
3. 목표 재고 값이 DOM에 처음 나타난 시각·관측 버전/cursor를 기록하고 두 animation frame 뒤 같은 값과 가시성을 확인한다. 물리적 모니터 표시를 측정하지 않는다. 브라우저 응답을 대체하지 않으며 API 요청은 모두 GET이고 인증 헤더가 없다.
4. 실제 페이지 버전/cursor를 영속 journal의 run·버전·상품/재고와 대조한다. 실제 관리자 POST와 변경 후 재고·예약 0도 별도 대조한다. timeout/미실행은 명부에 유지하며 0ms로 채우지 않는다.
5. 발생 시점이 helper 호출 구간 `[시작, 완료]` 안에 있다는 조건에서 `max(0, 화면−완료)`와 `화면−시작`을 하한/상한으로 구한다. 두 분포의 nearest-rank 분위수를 별도로 보고한다. 호스트/브라우저의 wall/monotonic 급변은 검사하지만 프로세스 사이의 시계 동기화를 증명하지는 않는다.

## 결과와 분모

| 실행 | 계획 / 반영 / timeout / 미실행 | p50 하한~상한 | p95 하한~상한 | 최대 하한~상한 |
|---|---|---|---|---|
| 첫 실행 `cw00-aa0d621af3e4-buyer` | 20 / 20 / 0 / 0 | 810~834ms | 1,011~1,046ms | 1,386~1,416ms |
| gate 종료 후 `cw00-fd75cf52f34e-buyer` | 20 / 20 / 0 / 0 | 703~741ms | 1,275~1,316ms | 1,345~1,377ms |

첫 실행 도중 `make check`가 겹쳤다. 이를 삭제하거나 두 번째 실행과 합산하지 않고 `concurrent-gate/`에 별도로 보존했다. gate의 종료 코드 0을 확인한 뒤 두 번째 실행을 시작했다. 다른 호스트 작업까지 없었다는 뜻은 아니다. 성능 통과 기준을 만족할 때까지 재시도하지 않았다.

두 번째 실행의 가장 느린 5번 변경은 helper 완료→관측 생성 837.305ms, 관측→게시 180.228ms, 게시→수신 304.037ms, 수신→probe 화면 23ms다. 이 합은 하한 1,344.570ms와 일치한다. 소스의 조회 루프는 조회 후 1초 대기, 게시 루프는 0.2초, SSE 확인은 0.5초 대기다. **외부 상태를 다음 조회까지 기다리는 구간이 포함되므로**, 이 결과를 내부 이벤트 전달만의 1초 목표 실패나 성공으로 해석하지 않는다. 구간별 p95들을 더해서 전체 p95를 만들지도 않는다.

각 20건의 실제 POST·변경 응답·화면·journal·상하한·분위수를 복사본에서 독립 재계산했다. 두 명부의 40건 모두 일치했다. 실제 구매·모델 호출은 0회다. 주문·납품·재접속·장시간/병렬 부하의 분포는 이 20건에 포함되지 않는다.
