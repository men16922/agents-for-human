# 관측 지연 표본 — CW06

2026-09-08. 로컬 Medusa 실행 `cw00-002ddeffbd43`에서 브라우저 수신 24건, 상태 반영 22건을 계측했다. 관측→반영 p95는 966ms였지만, 이전 버전·중복으로 반영하지 않은 지연 납품 알림 2건은 이 분모에 없다. 전체 이벤트의 1초 목표 달성이나 실제 모델 효과를 입증하는 결과는 아니다.

## 계측 계약

- 서버는 조회 시작의 epoch 시각과 monotonic 소요 시간을 기록한다. 관측 생성 시각·게시 시각은 영속 journal에 남아 재전달 시에도 유지된다. 기존 기록의 누락 시각을 0으로 채우지 않는다.
- 브라우저는 수신 시각을 epoch/monotonic으로 기록한다. React commit 이후 두 번째 animation frame을 반영 시점의 근사값으로 쓴다. 물리적 화면 표시를 직접 측정하지는 않는다.
- 현재 브라우저 실행별 최대 2,000개 표본을 보존하며 p50/p95/max는 보존 표본의 nearest-rank다. 비어 있는 분포는 null이다. 전체 수신·제외·재접속 수와 퇴출 수는 별도로 남긴다.
- 조회 소요 시간은 보존 구간의 고유 event ID가 분모다. 관측→게시·게시→수신은 중복/이전 버전을 포함한 전달 건수다. 반영 관련 세 구간은 실제 반영된 상태가 분모다. 서버의 모든 조회 시도나 외부 거래 수와 같지 않다.
- 반영 전에 새 상태가 적용되면 `superseded`, 숨겨진 화면은 `hidden`, 미반영/대기는 `not_applied`/`pending`으로 제외한다. 누락 시각과 시계 역전도 사유를 남긴다. 수신→반영의 epoch/monotonic 차이가 100ms를 넘으면 교차 시계 구간을 제외하고 유효한 로컬 monotonic 구간만 유지한다.
- 서버 프로세스별 조회 attempted/completed/failed/unchanged/in_flight의 첫·마지막 관측값을 최대 32개 프로세스까지 보존한다. 재시작 전후를 하나의 연속 카운터로 합치지 않는다. 연결 밖 구간이나 중단 당시 조회 결과를 추정하지 않는다.
- UI에서 전체/납품/상태/시계/초기 관측을 선택하고 JSON을 저장할 수 있다. JSON에는 원시 표본, 유형별 분포, 제외 사유, 커서 간격·reset·재접속 카운터가 포함된다. 다운로드는 브라우저 로컬에서 수행한다.

구현: [journal](../../src/rehearsal/commerce/observations.py), [observer](../../src/rehearsal/commerce/observer.py), [표본 집계](../../web/src/metrics.ts), [화면](../../web/src/MetricsPanel.tsx).

## 실제 실행 결과

`make commerce`로 전용 서비스를 시작한 뒤 `make commerce-observer-smoke`를 실행했다. 실제 A 재고 10→0, 거절 후 스크립트의 B 380 구매·수령 9·예약 0·독립 COMPLETE, observer 중단/재접속을 확인했다. control 경계에서 납품 알림에 2,000ms 지연과 2회 전달을 설정했다. 브라우저 응답은 mock으로 대체하지 않았다.

단위는 ms이며 아래 값은 반올림했다.

| 구간 | 유효 n | p50 | p95 | 최대 | 제외 n |
| --- | ---: | ---: | ---: | ---: | ---: |
| 서버 조회 소요 | 23 | 102 | 121 | 124 | 0 |
| 관측→게시 | 24 | 100 | 2,167 | 2,167 | 0 |
| 게시→브라우저 수신 | 24 | 282 | 796 | 830 | 0 |
| 수신→반영 | 22 | 35 | 45 | 47 | 2 |
| 관측→반영 | 22 | 409 | 966 | 983 | 2 |
| 조회 시작→반영 | 22 | 482 | 1,028 | 1,068 | 2 |

이벤트 수신 24 = 적용 22 + 이전 버전 1 + 중복 1이다. 전체 프레임 72 = observation 24 + status 47 + bridge_error 1이며, 연결 시도 2·중단 1·invalid 0·표본 퇴출 0·관측된 커서 공백 0이다.

지연 납품 알림은 게시까지 2,167.376ms가 걸렸다. 그 사이 더 최신 상태를 담은 전체 관측이 도착했으므로 첫 알림은 이전 버전, 재전달은 중복으로 처리됐다. 납품 유형의 전달 표본은 2개지만 반영 표본은 0개다. 지연 알림을 반영 분모에서 제외하면서 게시 지연까지 숨기지 않도록 유형별 분포와 원시 표본을 함께 보존했다.

서버 프로세스도 2개를 관측했다. 첫 프로세스의 마지막 상태는 시도 22·완료 21·진행 중 1이고, 둘째는 시도/완료 2다. 첫 프로세스의 미완료 조회를 성공이나 실패로 확정하지 않는다. 이 수치를 단순히 합산해 전체 실행의 조회 성공률로 쓰지 않는다.

## 남은 범위

외부 거래 발생 시각과 시계 동기화는 측정하지 않았다. 설계의 내부 이벤트→화면 p95 1초 목표를 이 소규모 로컬 실행의 관측→반영 값만으로 통과 처리하지 않는다. 조회 시작→반영 p95는 1초를 넘었으며 납품 지연 표본은 별도 분모다. 많은 주문·장시간 실행·부하·여러 기기·실제 모델 재계획도 미검증이다.

후속 [두 브라우저 검사](two-browser-recovery.md)에서 같은 run의 상태 일치, 한쪽 연결 중단 중 세계 진행, 각 커서로 복구 후 수령/예산/주문/재고 일치, retention 초과 snapshot 복구를 실제 검증했다. 전체 지연 목표와 모델 재계획은 여전히 별도다.

후속 [발생 시각/분모 감사와 재고 변경 계측](source-latency.md)에서 기존 24개 표본을 재대조하고 실제 변경 20건×2를 요청 구간·화면·영속 journal과 연결했다. 외부 조회 대기를 포함한 조건부 지연 범위이며 이 문서의 관측 이후 지연과 분리한다.
