# CW05 준비 — 동결 정책과 B0의 연습·Medusa 실행

2026-09-07. 정책 파일·프롬프트·실행 소스의 버전을 동결하고, 같은 B0 고정 규칙 실행자를 연습 세계와 독립 Medusa 구매 HTTP에 연결했다. 알려진 가격 변경/응답 유실과 부분 조달 조건을 실행했다. **학습된 정책의 전이, 실제 LLM·Peer Review 효과, 미공개 조건 평가, CW05 전체 완료는 아니다.**

2026-09-09 보충: 수정 B0의 기존 6개 결과 유지와 필수 품목 부족 2개를 [실제 Medusa 재검증](b0-medusa-rerun.md)으로 확인했다. 현재 명령은 총 8개를 실행하며 아래 표는 최초 6개 기록이다.

## 재현과 증거

`make commerce`가 준비된 뒤 별도 터미널에서 `make commerce-transfer-smoke`. 이 명령은 두 정책을 먼저 저장하고 3개 조건을 두 환경에서 실행한다. 고객/판매자 gateway 프로세스는 검사 후 종료한다. 마지막에 Medusa 터미널의 Ctrl+C로 전용 서비스를 종료하며 데이터와 볼륨을 보존한다.

- [고정된 입력 두 개와 결과](../../evidence/cw05-frozen-b0/report.json), [6개 실행 요약](../../evidence/cw05-frozen-b0/results.json).
- [갱신 전 정책](../../evidence/cw05-frozen-b0/before.json), [견적 갱신 정책](../../evidence/cw05-frozen-b0/revised.json).
- [동결 구현](../../src/rehearsal/experiments/frozen.py), [B0 실행자](../../src/rehearsal/experiments/baseline.py), [실제 대조 검사](../../scripts/commerce/transfer_smoke.py).
- [동결·SDK·B0 회귀 검사](../../tests/experiments/test_baseline.py). `make check`에서 외부 호출 없이 실행한다.

각 조건의 `practice`/`medusa` 폴더에는 실행 보고서·도구 trace·독립 원장 증거가 있다. 상위 보고서는 하위 파일 hash를 기록한다. DB·고객/판매자 비밀값·전체 fixture HTTP는 `.local/transfer`와 `.local/commerce`의 Git 제외 경로에 남는다. 공개 보존 파일에는 실제 자격증명이 없다.

## 동결한 내용과 실행 범위

정책의 공급처 선호·견적 갱신·후보 수·대기 간격·불확실 지급 처리 값을 JSON으로 저장한다. 정책 내용·프롬프트 SHA-256·실행 소스 hash·알려진 학습 자료 hash를 포함한 전체 내용으로 `frozen_id`를 계산한다. 기존 파일을 덮어쓰지 않고, 실행 전에 정책·프롬프트·지정 소스가 바뀌지 않았는지 검사한다. 학습 자료의 hash 연결은 채택/검토 완료나 독립 평가 통과를 뜻하지 않는다.

Strands의 `agent_for_tools(..., policy=...)`와 CW03 runner의 `--policy <manifest>` 입력도 추가했다. 실제 SDK + 스크립트 모델 검사에서는 정책을 system prompt로 전달하고 실행 보고서에 동결 ID·실제 프롬프트 hash·가상 usage 기록을 남겼다. `--policy`를 생략하면 기존 단일 실행자 경로를 유지한다. 실제 모델 CLI는 명시적인 모델/비용 설정과 `--execute`가 필요하며 이번에는 실행하지 않았다.

B0는 평가 계획에 있던 고정 규칙 비교군이다. 전체 잔여 물품의 견적을 먼저 비교하고 실행 가능한 견적이 없으면 품목별 견적을 조회한다. 한 구매의 지급/납품을 확인한 다음 실제 수령량을 빼서 다음 구매를 계획한다. 견적 거절을 실제 재고 전체의 불가능 판정으로 확대하지 않으며, 실행 가능한 견적이 없으면 미완료로 끝낸다. 이 휴리스틱의 전역 최적성은 주장하지 않는다.

미확정 지급은 같은 주문만 조회한다. 시작 시 이전 예약이 남아 있으면 새 주문을 만들지 않고 `UNKNOWN`으로 멈춘다. B0는 구매 도구 8개만 받으며 admin·세계 DB·seed·장애 계획을 받지 않는다. 장애는 별도 실험 운영자가 주입한다. 도구 호출 상한은 80, 경과 시간 검사는 호출 전 180초다. 이는 현재 LLM 기본 상한 24회와 다르므로 B0와 LLM의 동등 예산 성능 비교 결과로 사용하지 않는다.

## 실제 관측

두 환경의 목표는 텐트 3개·조명 6개, 예산 500, 기한 120tick이다. 배송 지연은 A/B/C 4/6/8tick으로 맞췄다. 연습 tick은 가속되고 운영 tick은 실제 1초이므로 벽시계 처리시간의 우열을 이 표에서 비교하지 않는다.

| 알려진 조건 | 연습 결과 / 집행 / 도구 | Medusa 결과 / 집행 / 도구 |
|---|---|---|
| 견적 갱신 안 함, A 가격 변경 | 미완료 / 0 / 5회 | 미완료 / 0 / 5회 |
| 견적 갱신, A 가격 변경 + 지급 응답 유실 | COMPLETE / 380 / 20회 | COMPLETE / 380 / 20회 |
| 견적 갱신, 공급처별 일부 품목만 가능 | COMPLETE / 360 / 47회 | COMPLETE / 360 / 47회 |

첫 조건은 A의 기존 견적으로 주문하다 거절됐다. 정책이 중단했으며 기한까지 기다린 실패 실험은 아니므로 독립 판정은 `INCOMPLETE`다. 지급에 도달하지 않아 응답 유실은 발생하지 않았다. 두 번째 조건은 새 견적에서 B를 선택했다. Medusa에서는 실제 상품 가격 60→100과 gateway 응답 지연 1.2초/고객 timeout 0.4초를 사용했다. 지급 요청은 1회였고 같은 주문 조회로 수령을 확인했다.

부분 조달 조건은 A 조명 0, B 텐트 0, C 두 품목 0으로 구성했다. Medusa의 실제 inventory location API로 초기 재고를 바꾼 뒤 실행했다. B에서 조명 6개(170)를 받고 A에서 텐트 3개(190)를 추가해 합계 360이었다. 이미 받은 조명을 다시 구매하지 않았다. 이는 F04의 알려진 사례이며, 연습 도중 다른 참여자가 재고를 소진하는 동시 외부 변경 검증은 남았다.

각 환경은 별도 독립 검증기로 판정했다. B0의 `GOAL_OBSERVED` 보고 자체를 성공의 근거로 사용하지 않는다. 두 환경에서 같은 동결 ID를 유지했고, 매 실행은 새 고객/원장·동일한 명시적 가격/재고 조건에서 시작했다. 이 6개 실행은 전체 실패/중단을 포함한 알려진 fixture 점검이며, 본 평가의 20개 미공개 조건이나 현실 성공률의 분모가 아니다.
