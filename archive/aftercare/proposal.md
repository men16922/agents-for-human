# Aftercare

배포 후 30분, 확인 업무까지 맡기는 AI 운영 동료

**AWS Agents for Humans Hackathon · Professional Agents · 신규 프로젝트 기획 v1.0**  
작성: 2026-09-06 · 제출 마감: **2026-09-15 09:00 KST**  
문서 상태: **기획 완료 · 제품 구현 전 · 성과 미측정**

> **제안:** 소규모 개발팀의 배포 후 확인 업무를 맡는 에이전트를 새로 만든다. 배포 이벤트를 받으면 로그·버전·사용자 요청 결과를 살펴보고, 사전에 허용된 범위에서 조치한 뒤 회복을 확인한다. 자동으로 끝낼 수 없는 경우에는 근거와 필요한 결정 하나를 담아 담당자에게 인계한다.
>
> **최고득점 전략:** 복잡한 플랫폼보다 한 사람의 반복 업무를 완결하는 제품을 만든다. 핵심 데모는 **“배포도 성공했고 HTTP도 200인데, 사용자에게 돌아가는 결과가 틀렸다”**는 상황이다. 발견 → 조사 → 실제 조치 → 재확인까지 한 흐름으로 증명한다. 최고득점은 목표이며 예상 점수나 수상을 보장하지 않는다.

이 문서는 제품과 실행 계획을 정의한다. 클라우드 배포, 지출, 계정 변경 또는 외부 게시를 실행한 기록은 아니다. 아래 예시 화면·장애·목표 수치는 모두 **설계 예시 또는 검증 목표**다.

## 02. 왜 이 문제인가

### 사용자에게 남아 있는 일

배포가 끝나도 개발자의 일은 끝나지 않는다. 배포 도구의 성공 상태를 보고, 로그를 열고, 사용자 요청을 다시 보내고, 이상이 배포 때문인지 외부 의존성 때문인지 확인한다. 되돌린 뒤에도 같은 확인을 반복한다. 사람에게 넘겨야 한다면 지금까지의 관측과 시도를 다시 정리한다.

**문제 가설:** 소규모 팀은 이 확인 업무를 맡길 운영 인력이 부족하고, 단순한 알림이나 요약만으로는 화면을 계속 확인하는 시간을 충분히 줄이지 못한다. 실제 빈도와 소요 시간은 사용자 검증 전이며 시장 통계처럼 주장하지 않는다.

**해야 할 일:** “내가 배포를 끝내면, 이 변경이 사용자에게 정상적으로 동작하는지 확인하고 허용된 대응까지 맡아줘. 내가 결정해야 할 일이 생기면 왜 필요한지 함께 알려줘.”

### 출발점이 된 경험

비공개 `platform-agent`를 개발하면서 실행 결과, 검증 결과, 최종 보고가 서로 다른 사실을 표현할 수 있음을 확인했다. 조치가 호출됐다는 사실만으로 회복이 확인되는 것은 아니며, 관측이 없다는 사실도 정상이라는 뜻이 아니다. GitOps가 롤백을 다시 덮는 사례처럼 조치 직후의 성공이 유지되지 않는 상황도 있다.

Aftercare는 이 경험에서 **배포 이후 담당자가 반복하는 확인 업무**를 뽑아 신규 제품으로 만든다. 부모 플랫폼의 멀티클라우드·테넌트 관리·전체 기능을 옮기지 않는다. 기존 코드나 작업을 실제로 편입하게 되면 그 범위를 제출 설명에 사실대로 적는다.

### 해결했을 때 달라지는 하루

개발자는 매 배포마다 대시보드를 순회하는 대신, 맡긴 관측 기간 동안 원래 업무로 돌아간다. 정상 건은 종료 요약만 남는다. 이상 건은 에이전트가 근거를 모으고 허용된 조치를 진행한다. 담당자에게는 해결되지 않은 이유와 선택지가 정리된 상태로 전달된다.

성공의 단위는 “알림을 몇 개 보냈는가”가 아니라 **사람이 직접 확인한 시간과 다시 열어야 했던 화면을 얼마나 줄였는가**다.

## 03. 후보 비교와 선택 근거

| 후보 | 강점 | 이번 일정의 약점 | 결정 |
|---|---|---|---|
| BillBuddy | 이해하기 쉬운 생활 문제 | 사용자 정의가 넓고 실제 금융 작업 연결이 무거움 | 보류 |
| 플랫폼 전체의 자연어 운영 | 기존 설계 경험이 풍부함 | 5분 동안 제품의 핵심이 분산됨; 신규 제출 범위도 커짐 | 제외 |
| 장애 대응 문서 리허설 | 실패 전후를 재현하기 쉬움 | 문서 검증으로 가치가 좁아지고 실제 운영 인계 경험은 약함 | 후속 아이디어 |
| **Aftercare** | 문제 경험·제어 가능한 실환경·사람의 시간 절감이 연결됨 | 기존 운영 도구와 차이를 실증해야 함 | **선택** |

선정 근거는 기술을 이미 안다는 사실만이 아니다. **새로운 사용자가 이해할 수 있는 문제를, 남은 기간에 실제 동작과 측정으로 보여줄 수 있는가**를 우선했다. 기존 코드의 테스트 수를 신규 제품의 검증 실적으로 가져오지 않는다.

## 04. 기존 도구와 어떻게 비교할 것인가

| 비교 대상 | 공식 문서에서 확인한 기능 | Aftercare가 입증해야 할 선택 이유 |
|---|---|---|
| AWS CodeDeploy | 배포 실패·알람 조건에 따른 자동 롤백 | 알람 임계값을 넘지 않는 기능 오류의 조사와 담당자 인계까지 연결 |
| AWS DevOps Agent | 자율 조사, 로그·지표·변경 분석, 완화 제안, 배포 관련 지원 | 한 서비스에 제한된 연결 절차와 배포 후 확인 업무의 완결성 |
| PagerDuty SRE Agent | 조사, 승인된 복구, 회복 확인 | 명시적인 관측 계약과 사용자 요청 결과를 포함한 간결한 처리 경험 |
| 수동 확인·팀의 스크립트 | 팀이 정의한 검사와 복구 절차 | 예상 밖 관측을 조사하는 유연성과 사람의 확인 시간 감소 |

근거: [CodeDeploy 롤백](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployments-rollback-and-redeploy.html), [AWS DevOps Agent](https://aws.amazon.com/devops-agent/faqs/), [자율 인시던트 대응](https://docs.aws.amazon.com/devopsagent/latest/userguide/production-operations-autonomous-incident-response.html), [PagerDuty SRE Agent](https://www.pagerduty.com/fr/platform/ai-agents/sre/). 확인일: 2026-09-06.

**차별화 가설:** “HTTP 성공 여부”에서 한 걸음 더 나아가 등록된 사용자 요청의 결과를 확인하고, 새 버전·이전 버전·외부 의존성의 관측을 비교해 다음 행동을 선택한다. 처리 결과에는 어떤 근거로 회복 또는 미검증을 판정했는지 남긴다.

이 기능들이 경쟁 제품에 없다고 주장하지 않는다. CodeDeploy에도 사용자 정의 검사·알람을 연결할 수 있다. 데모의 비교 대상은 **우리가 공개한 동일 환경·동일 검사 조건의 구현**이며, 상용 제품 전체를 재현한 비교가 아니다.

### 왜 고정 스크립트만으로 끝내지 않는가

복구 판정과 변경 권한은 결정론적 코드로 처리한다. 에이전트는 자유형 배포 설명·구조화 로그·도구 결과에서 조사할 근거를 고르고, 관측에 따라 다음 도구를 바꾸며, 담당자가 이해할 수 있는 설명과 인계를 만든다.

평가에는 **동일 검사·동일 변경 권한을 가진 고정 실행 순서의 스크립트**도 포함한다. 에이전트가 설명만 덧붙이고 조사 품질이나 사람의 시간을 개선하지 못하면, Strands가 필요한 이유를 입증하지 못한 것이다. 이 경우 기능을 늘리지 않고 조사 흐름을 다시 설계한다.

## 05. 첫 사용부터 종료까지

### 연결은 한 번, 감시는 배포마다

1. 개발자가 서비스·alias·등록된 검사·이전 정상 버전·담당자를 연결한다.
2. 관측 기간과 변경 정책을 선택한다. 기본 관측 기간 **30분은 제품 설계값**이며 사용자 피드백으로 조정한다.
3. 배포 시스템의 성공 이벤트가 들어오면 자동으로 관측을 시작한다.
4. 로그와 요청 결과가 이상하면 에이전트가 조사한다. 정상일 때는 모델을 반복 호출하지 않는다.
5. 허용된 조치는 수행하고, 그 이후 새로 얻은 표본으로 다시 확인한다.
6. 관측 기간 종료 또는 인계 완료 시 작업을 닫는다. 문제가 풀리지 않은 상태를 정상 종료로 표시하지 않는다.

### 화면 구성

| 화면 | 사용자에게 먼저 보이는 것 | 상세에서만 보이는 것 |
|---|---|---|
| 서비스 목록 | 지금 맡긴 서비스, 상태, 남은 관측 시간 | 리소스 식별자·연결 정보 |
| 배포 카드 | 현재 상황, 사용자 영향, 에이전트의 다음 행동 | 버전·alias revision·검사 원문 |
| 판단 요청 | 필요한 선택 하나, 이유, 선택별 결과 | 실행 범위·변경 전후값·승인 만료 |
| 종료·인계 기록 | 처리 결과와 아직 모르는 점 | 관측 표본·도구 호출·요청 ID·시간 |

메인 화면은 채팅창이 아니다. 자연어 입력은 상황 설명이나 추가 질문에만 쓴다. 오류·연결 끊김·측정 중·일시적 회복을 서로 다른 상태로 표시한다.

> **화면 문구 예시 · 실측 아님**  
> “배포는 완료됐지만 배송비 계산 결과가 예상과 다릅니다. 이전 버전에서는 같은 검사가 통과했습니다. 허용된 이전 버전으로 되돌리고 있습니다.”  
> “이전 버전에서도 같은 오류가 발생합니다. 추가 롤백은 하지 않았습니다. 배송 권역 조회 서비스의 응답을 확인해야 합니다.”

정상 종료는 알림을 늘리지 않도록 카드와 일괄 요약에 남긴다. 즉시 알림은 승인 요청, 관측 불가의 지속, 기한 내 미해결처럼 사람이 개입해야 하는 경우에 보낸다. 사용자는 언제든 관측과 자동 변경 권한을 중단할 수 있다.

## 06. MVP의 경계

### P0 — 제출 전에 반드시 동작할 것

| 기능 | 완료 조건 |
|---|---|
| 배포 이벤트 자동 수신 | 브라우저를 닫아도 배포 이벤트로 작업이 시작됨 |
| Strands 조사 루프 | 실제 Bedrock 호출과 도구 선택 기록; 상황에 따라 조사 순서가 달라짐 |
| 등록된 기능 검사 | HTTP 상태와 응답 내용의 계약을 함께 검사; 실패·시간초과·빈 표본 구분 |
| 현재·이전 버전 대조 | 같은 입력으로 관측하고 요청 ID·버전·시각을 기록 |
| 제한된 실제 롤백 | 사전 등록 버전과 alias에 대해서만 조건부 변경; 변경 결과를 재조회 |
| 회복 확인 | 변경 이후 표본으로 별도 판정; 표본 부족이면 종료하지 않음 |
| 승인·거절·중단 | 서버에 남고 새 요청에서 이어짐; 이전 승인이 다른 변경에 재사용되지 않음 |
| 종료·인계 카드 | 원래 증상·시도·관측·남은 결정이 한 화면에 정리됨 |
| 공개 평가 환경 | 실제 AWS 실행 경로, 데이터 초기화, 사용자별 작업 구분, 실행 횟수 제한 |

### P1 — P0 실증 후에만 추가

Slack 알림 한 종류, 관측 이력 검색, 반복 배포에 대한 간단한 팀 요약. AgentCore Runtime은 기본 배포 계획에 포함하되 연결 문제로 핵심 흐름이 지연되면 Strands를 유지한 Lambda 실행으로 우선 닫는다.

### 이번에 만들지 않을 것

멀티클라우드·EKS 플랫폼·자율 코드 수정·임의 셸 실행·새 인프라 생성·전체 FinOps·일반적인 인시던트 관리 제품·네 개의 전문 에이전트·학습된 선호에 따른 자동 권한 확대. 별도의 SDK 기능을 보여주기 위한 Memory나 MCP도 넣지 않는다.

**MVP 성공은 P0의 완결성으로 판단한다.** 기능 수나 소스 줄 수를 성공 조건으로 쓰지 않는다.

## 07. AWS와 Strands의 역할

```text
배포 이벤트 / 주기적 관측 tick / 사용자 승인
                     │
          EventBridge → Dispatcher Lambda
                     │
        작업 상태·잠금·기한 확인 (DynamoDB)
                     │
        AgentCore Runtime ─ Strands Agent
                │              │
                │         Amazon Bedrock
                │       조사 계획·도구 선택·설명
                ▼
          명시적인 업무 도구
     ┌──────────┼─────────────┐
  배포·로그 읽기  등록 검사 실행   변경 요청 준비
     │          │             │
 CloudWatch   API Gateway /   정책 검사 → Executor Lambda
 Lambda 정보   Lambda 버전      지정 alias 조건부 변경
     └──────────┼─────────────┘
                ▼
      독립 회복 판정기 + 관측·실행 기록
                │
          DynamoDB / S3 evidence
                │
      인증된 API → 웹 카드 / 선택적 알림
```

프런트엔드는 TypeScript로 작성하고 S3 + CloudFront에서 제공한다. API Gateway + Lambda를 업무 API로 두고 Cognito로 사용자와 작업을 연결한다. 공개 데모의 쓰기 경로도 인증·사용량 제한을 적용하며 브라우저에 AWS 자격증명을 주지 않는다. 인프라는 CDK TypeScript로 재현한다.

| 구성요소 | 맡는 일 | 맡기지 않는 일 |
|---|---|---|
| Strands Agent | 근거 탐색·도구 선택·가설 수정·사람에게 설명 | 권한 확대, 성공 기준 변경 |
| Bedrock | 실제 모델 추론 | 고정 시나리오에 맞춘 결과 재생 |
| AgentCore Runtime | 에이전트 실행과 세션 | 작업 장부·잠금·승인 상태의 유일한 저장소 |
| Dispatcher | 중복 이벤트 제거·기한·버전·실행 예산 확인 | 원인 분석 |
| Executor Lambda | 허용된 변경만 실행·결과 대조 | 임의 리소스 변경·셸 실행 |
| 회복 판정기 | 버전·시간·표본·기능 계약을 코드로 평가 | 모델의 자기 평가를 그대로 승인 |
| DynamoDB·S3 | 작업·승인·관측·증거 저장 | LLM 대화만으로 상태 복원 |

### Strands 도구 계약

| 도구 | 입력·결과의 핵심 | 실제로 필요한 이유 |
|---|---|---|
| `inspect_release` | 등록 서비스의 현재/이전 버전·alias revision·배포 설명 | 조사 시작점과 변경 충돌 확인 |
| `read_evidence` | 등록 로그·관측의 시간 범위, 출처가 있는 결과 | 일반 로그와 기능 오류를 함께 해석 |
| `run_registered_probe` | 검사 ID와 허용 대상; 상태·본문 판정·버전·시각 | 현재/이전 버전·의존성 대조 |
| `prepare_action` | 대상·기대 revision·허용 버전·근거 ID | 사용자에게 검토 가능한 변경안 제시 |
| `execute_approved_action` | 서버에 저장한 변경안 ID | 정책 검사 뒤 실제 alias 변경 |
| `request_handoff` | 증거 ID·남은 문제·필요한 결정 | 미해결 상태를 누락 없이 인계 |

승인 흐름은 Strands interrupt/resume를 사용한다. 중단 이후 필요한 상태를 서버에 저장하고 새로운 요청으로 복원하는 테스트를 둔다. 메모리에 남아 있는 대화가 있어야만 승인이 동작하는 설계는 피한다. SDK 버전·모델 ID·리전은 첫 실증에서 확인한 조합으로 고정한다. [Strands interrupts](https://strandsagents.com/docs/user-guide/concepts/interrupts/)

AgentCore 세션에는 실행 수명과 유휴 종료 조건이 있다. 30분 동안 프로세스 안에서 대기하는 대신 짧은 실행과 저장된 상태로 이어 간다. 정상 관측 tick은 결정론적 검사만 수행하고, 새로운 이상이나 판단이 있을 때 모델을 호출한다. [AgentCore 세션](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)

## 08. ‘회복됐다’고 말할 수 있는 조건

### 관측 계약

서비스 연결 시 담당자가 검사와 통과 조건을 등록한다. LLM은 이 조건을 수정할 수 없다. 데이터가 없거나 출처를 확인할 수 없으면 **미검증**이다.

첫 데모 서비스의 조건은 다음과 같이 시작한다. 모두 **제품 검증을 위한 제안값**이며 일반 서비스의 SLO나 통계적 보장은 아니다.

- 부작용 없는 배송비 견적 요청 5개를 한 관측 묶음으로 실행한다.
- 각 요청은 HTTP 응답뿐 아니라 필수 필드·정해진 입력의 예상 결과를 검사한다.
- 변경 완료 시각 이후에 수집한 **서로 다른 두 묶음**이 통과해야 회복 확인 후보가 된다.
- 모든 표본에 검사 ID·실제 실행 버전·UTC 시각·요청 ID·결과를 남긴다.
- 두 묶음 사이의 간격은 데모와 기본 모드 모두 명시한다. 데모는 **15초 제안값**, 기본 모드는 **60초 제안값**으로 시작한다.
- 회복 확인 후에도 남은 관측 기간 동안 확인하며 재악화하면 사건을 다시 연다.
- 직접 검사와 CloudWatch 관측이 충돌하면 차이를 조사한다. 지표가 없는 것을 0으로 채우지 않는다.

데모의 15초 간격 재검사는 실행 시간이 제한된 probe worker 한 번 안에서 처리한다. EventBridge에 15초 주기를 설정하는 구성으로 설명하지 않는다. 기본 관측은 1분 tick과 저장된 작업 상태를 사용한다.

10개 표본의 성공은 장기 신뢰성의 증명이 아니다. 사용자에게는 **등록 검사에서 관측한 회복**이라고 표시한다. CloudWatch 지표의 timestamp·dimension·집계 구간을 보존하고, 조치 전 표본을 조치 후 결과로 섞지 않는다. [CloudWatch 지표 개념](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html)

### 상태와 권한

| 관측 상태 | 표시 | 다음 행동 |
|---|---|---|
| 배포 완료·검사 대기 | 관측 중 | 검사 예약 |
| 기능 오류가 확인됨 | 영향 확인 | 근거 조사 |
| 변경 API 성공 | 조치 완료·재확인 중 | alias 재조회와 새 표본 수집 |
| 등록된 회복 조건 충족 | 회복 확인·관측 유지 | 남은 기간 감시 |
| 기한 종료·정상 관측 충족 | 관측 완료 | 종료 요약 |
| 표본 없음·출처 불명·도구 장애 | 미검증 | 제한된 재시도 후 인계 |
| 기한 내 미회복 | 판단 필요 | 시도와 근거를 묶어 인계 |

자동 변경은 **사전 위임 + 지정 서비스/alias + 허용된 이전 버전 + 최신 revision 일치 + 유효한 근거 + 실행 횟수·기한 이내**를 모두 만족해야 한다. 한 배포당 자동 rollback은 최대 1회로 시작하며 재실행보다 결과 조회를 우선한다. 되돌린 버전이 안전한지는 데이터·스키마 호환성을 포함해 서비스 소유자가 사전에 승인해야 한다.

`UpdateAlias`에는 읽어 둔 `RevisionId`를 전달한다. 충돌하면 다시 읽고 변경안을 폐기한다. 새 변경안에 이전 승인을 자동 승계하지 않는다. 시간초과 뒤에는 alias를 조회해 결과를 확인하고, 결과 불명 상태를 성공이나 무조건 재시도로 처리하지 않는다. [Lambda UpdateAlias](https://docs.aws.amazon.com/lambda/latest/api/API_UpdateAlias.html)

### 실행 경계

에이전트 실행 역할에는 직접 `UpdateAlias` 권한을 주지 않는다. 실행기는 해당 데모 함수·alias로 한정한 별도 역할을 사용하며, 도구 본문에서도 허용 대상·revision·승인·기한을 다시 확인한다. 로그와 배포 설명에 들어 있는 명령은 신뢰하지 않는다. 검사 URL을 사용자가 임의로 지정하지 못하게 하고 등록 대상만 호출한다.

중복 배포 이벤트는 서비스·배포 ID로 합치고, DynamoDB 조건부 쓰기로 실행을 직렬화한다. 잠금 소유자와 상태 버전을 검사해 만료된 작업자가 새 작업의 변경을 수행하지 못하게 한다. 화면의 중단 버튼은 서버의 실행 허가를 회수한다. 데이터 TTL은 보관 정책이며 작업 종료 타이머로 쓰지 않는다.

## 09. 5분 데모: 초록 화면 뒤의 잘못된 결과

### 실제 환경

AWS에 **배송비 견적 API**를 새로 배포한다. 주문 생성·결제·개인정보는 없다. 정상 버전과 기능 오류가 있는 버전, 등록된 검사 입력, 통제 가능한 권역 조회 의존성을 준비한다. API Gateway → Lambda alias → 응답이 실제로 동작한다.

결과는 고정하지 않는다. 결함과 외부 조건을 통제하고, 에이전트는 실제 도구 결과로 판단한다. 장애 주입기는 평가용 별도 역할이며 에이전트에는 장애 종류·정답·복구 스위치를 노출하지 않는다.

### 세 가지 필수 시나리오

| 사례 | 실제로 만드는 상황 | 기대하는 행동 | 핵심 증거 |
|---|---|---|---|
| **A. 성공처럼 보이는 배포** | 새 버전이 HTTP 200을 반환하지만 특정 배송비를 잘못 계산 | 기능 오류 감지 → 이전 버전 대조 → 허용된 alias rollback → 재검사 | alias·버전 변경, 응답 값, 요청 ID, 두 관측 묶음 |
| **B. 되돌려도 풀리지 않는 문제** | 권역 조회 의존성이 실패해 현재/이전 버전 모두 영향 | 같은 근거로 무의미한 rollback을 반복하지 않고 의존성 조사·인계 | 버전별 검사 결과와 쓰기 호출 횟수 |
| **C. 관측이 없는 상황** | 검사 실행 또는 증거 수집 경로가 끊김 | 미검증 유지 → 제한된 재시도 → 판단 요청 | 표본 0을 정상으로 표시하지 않는 화면 |

추가 검증 D는 동시 배포로 revision이 달라지는 상황이다. 영상에는 여유가 있을 때 짧게 넣고, 테스트와 실행 기록에는 반드시 포함한다.

### 영상 구성 — 4분 40초 목표

| 시간 | 보여줄 내용 |
|---|---|
| 0:00–0:25 | 작은 팀의 개발자가 배포 뒤 반복하는 확인 업무와 대상 사용자 |
| 0:25–0:45 | 연결된 서비스·미리 정한 검사·자동 조치 범위 |
| 0:45–2:25 | 사례 A: 실제 배포 이벤트 → HTTP 200의 잘못된 결과 → 조사 → rollback → 회복 확인 |
| 2:25–3:10 | 사례 B: 이전 버전도 실패 → 다른 근거 수집 → 인계 카드 |
| 3:10–3:40 | 사례 C: 표본이 없을 때 미검증으로 남는 화면 |
| 3:40–4:10 | Strands가 선택한 도구와 AWS 실제 변경·관측 기록 |
| 4:10–4:40 | 실제 측정한 사용자 시간·검증 결과·지원 범위 |

세 사례는 별도의 실시간 실행을 촬영하고 컷 전환을 표시한다. 30분 감시를 5분 영상 안에서 완료했다고 주장하지 않는다. 데모 프로파일의 짧은 관측 간격을 화면에 표시하고, 기본 30분 프로파일의 별도 실행 기록도 남긴다. 표본·요청·시간을 편집으로 만들어내지 않는다.

## 10. 심사 항목별 고득점 전략

공식 심사는 다섯 항목에 동일 비중을 둔다. 아래는 **내부 목표와 증거 계획**이며 예상 심사 점수가 아니다. AgentCore와 live demo는 기술 평가를 강화하는 요소이고, Strands는 필수다. [공식 개요](https://agentsforhumans.devpost.com/), [공식 규정](https://agentsforhumans.devpost.com/rules)

기술이 앞서도 제품 경험과 효과가 약하면 높은 총점을 기대하기 어렵다. 구현 기간의 마지막 이틀은 새 기능보다 사용자 검증·화면·영상에 배정한다.

Builder Center 글은 실제 구현과 실패 경험을 담아 **최대 3편**을 목표로 한다. 규정상 편당 0.2점, 최대 0.6점 가산이며, 제목에 `Agents for Humans`를 포함하고 제출 마감 전에 공개해야 한다. 실제 소재가 충분할 때만 분리하고 같은 글을 재포장하지 않는다. [공식 규정](https://agentsforhumans.devpost.com/rules)

예정 소재: ① HTTP 200인데 기능 검사가 실패한 배포 ② 재시도·동시 배포에서 오래된 승인을 막은 방법 ③ 사용자 테스트에서 줄어든 확인 업무와 남은 한계.

## 11. 검증 계획과 출시 기준

### 기술 평가

24개 사례를 미리 정의한다. 기능 회귀·공유 의존성 문제·관측 문제·동시성/중복의 네 범주에서 각 6개를 구성한다. **12개 개발용 / 12개 최종 평가용**으로 분리하고 최종 평가의 정답은 에이전트 입력에서 숨긴다. 숫자는 데이터 준비 목표이며 확보 실적이 아니다.

최종 평가 12개를 각각 5회 반복해 60회 실행한다. 사례와 반복 실행을 구분해 보고한다. 같은 사례 5회를 독립 사용자나 독립 장애 5종처럼 세지 않는다. 실행 순서와 초기 상태를 고정·기록하고 모델·프롬프트·도구·검사 버전을 함께 남긴다.

| 지표 | 정의 | 제출 전 목표 |
|---|---|---|
| 잘못된 정상 종료 | 실제 실패·관측 부족인데 정상 종료한 횟수 / 해당 실행 수 | **관측된 0건**; 분모·검사 범위 표시 |
| 잘못된 변경 | 권한·기한·revision·대상 범위를 어긴 실제 변경 횟수 | **0건** |
| 중복 변경 | 동일 배포/변경안에 대한 중복 쓰기 횟수 | **0건** |
| 올바른 종료·인계 | 사례별 정답 상태와 일치한 실행 비율 | **90% 이상 목표**, 범주별 별도 보고 |
| 복구 완료 시간 | 이상 확인부터 등록 회복 조건 충족까지 | 실측 분포 보고; 미해결은 제외하지 않고 별도 표기 |
| 모델 지연·비용 | 실행당 모델 호출·토큰·처리 시간·사용액 | 모델과 리전 고정 후 실측; 아직 미측정 |

회복 판정은 에이전트가 작성한 설명과 별개로 검증한다. 테스트용 결함 상태, 실제 응답, alias revision, 도구 호출 장부를 대조한다. 핵심 권한·중복·표본 가드는 일부러 제거하거나 경계값을 바꾸어 검사가 실패하는지 확인한다.

### 사람의 시간 평가

본인 외 개발자 **3명 확보를 목표**로, 서로 비슷하지만 다른 배포 사례를 수동 도구와 Aftercare로 처리하게 한다. 사용 순서를 바꾸어 연습 효과를 줄인다. 계측은 직접 화면을 보고 판단·조작한 시간, 도구 전환 수, 결과를 잘못 이해한 횟수를 기록한다. 백그라운드 대기 시간과 사람의 작업 시간을 분리한다.

**내부 제품 목표:** 사람의 직접 확인 시간 중앙값 50% 감소, 필요한 인계를 이해하는 데 걸리는 시간 감소, 잘못된 정상 이해 증가 없음. 모두 미측정 목표다. 표본 3명으로 전체 시장의 생산성 향상을 일반화하지 않는다.

사용자를 확보하지 못하면 본인 1명의 평가라는 범위를 명시하고, 잠재 효과 주장을 낮춘다. 가상의 후기나 “팀에서 사용 중”이라는 문구를 만들지 않는다.

### 비교 실험

수동 CloudWatch/로그/검사, 문서화한 고정 순서 스크립트, Aftercare를 같은 장애·검사·권한에서 비교한다. 단순 임계값 알람만 쓰는 실험은 별도로 표시하며, 그것을 CodeDeploy 전체 성능이라고 부르지 않는다. Aftercare가 더 느리거나 더 많은 판단을 요구한 사례도 공개한다.

### 지출 계획

초기 개발·검증·촬영 지출 상한은 **US$40 제안값**으로 두고 사용 가능 크레딧과 실제 단가를 확인한 뒤 확정한다. 이는 현재 비용 추정이나 지출 승인이 아니다. AgentCore·Bedrock·CloudWatch·API Gateway·Lambda·DynamoDB·S3/CloudFront·인증 관련 사용액을 포함해 확인한다. 고정 컴퓨트와 NAT Gateway가 필요한 구성을 기본안에 넣지 않는다.

실측 전 월 비용을 제시하지 않는다. 사용량 장부에는 모델 호출·토큰·probe 수·관측 tick·작업별 리소스 사용량을 남기고, 단가를 적용한 추정과 결제계정의 실제 청구를 분리한다. AWS 예산 알림은 사후 알림이므로 실행 상한의 대체물로 쓰지 않는다.

공개 데모는 사용자별 일일 실행 수·동시 작업·probe·모델 호출 상한을 둔다. 최종 값은 하루 실제 사용량을 측정한 뒤 고정한다. 심사 기간에는 저사용량 실데모를 유지할 계획이며, 비용 상한 도달 시 새 실행을 중단하고 확인 가능한 테스트 빌드·기록을 제공한다. 그 상태를 live demo라고 표시하지 않는다. 심사 종료 후 별도 정리한다.

### One-line pitch

> **Aftercare takes the post-deployment watch off a developer’s plate—checking real application behavior, carrying out pre-approved recovery, and bringing back only the decisions that need a human.**

### 30-second pitch draft

> For small software teams, a successful deployment starts another job: checking dashboards, reading logs, testing requests, and deciding whether to roll back. Aftercare takes that watch. Built with Strands Agents, it investigates what changed, checks application behavior, and carries out recovery within limits the developer set. It then checks the result. If the evidence is missing or the problem needs a person, it hands over a concise account of what happened, what it tried, and what decision remains.

### 영상의 마지막 문장

> **You shipped the change. Aftercare stays to check the outcome.**

‘무중단 보장’, ‘완전 자율 SRE’, ‘사람이 필요 없는 운영’, ‘기존 제품 최초의 검증 기능’은 사용하지 않는다. 이 제품이 맡은 업무와 실제 확인한 결과를 보여준다.

## 14. 기획 검토에서 남은 질문

1. 실제 개발자에게 배포 직후 30분이 가장 부담스러운 구간인가, 배포 다음 날의 점검이 더 중요한가?
2. 기능 검사를 등록하는 초기 부담을 어느 정도까지 받아들일 수 있는가?
3. 한정된 자동 rollback과 승인 후 rollback 중 어떤 기본값을 신뢰하는가?
4. 고정 스크립트와 비교해 에이전트가 필요한 조사 상황을 충분히 확보할 수 있는가?
5. 공개 실데모를 심사 기간 동안 유지할 수 있는 사용량과 비용 상한은 얼마인가?

이 질문들은 기획서 작성의 선행 승인을 요구하는 항목이 아니다. **첫날 사용자 검토와 첫 실환경 실행에서 확인할 가설**이다. 우선 하나의 서비스·하나의 실제 변경·세 가지 상반된 관측을 완결하고, 그 결과로 범위를 조정한다.
