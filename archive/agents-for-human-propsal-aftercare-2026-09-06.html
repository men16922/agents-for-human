01. 배포 성공 뒤에도 남는 일

대상은 별도 SRE 없이 배포와 운영을 맡는 소규모 웹 서비스팀의 개발자다. 배포가 끝나면 로그를 열고, 실제 요청을 보내고, 문제가 새 버전 때문인지 외부 서비스 때문인지 확인한다. 되돌린 뒤에도 같은 확인을 반복한다.

Aftercare는 이 배포 후 확인 업무를 맡는다. 개발자는 서비스와 검사·조치 범위를 한 번 설정하고, 배포할 때마다 필요한 판단만 전달받는다.

제품의 목표는 개발자가 직접 확인하는 시간을 줄이는 것이다. 배포 직후 30분을 기본 관측 기간으로 제안하며, 실제 업무에 맞는 기간과 효과는 사용자 테스트로 검증한다.

02. 관측에 따라 다음 행동을 바꾼다

연결 → 자동 확인 → 조치 → 재확인·인계

  1. 연결: 서비스, 이전 정상 버전, 기능 검사, 담당자와 변경 정책을 등록한다.
  2. 관측: 배포 이벤트가 들어오면 백그라운드에서 응답 내용과 로그를 확인한다.
  3. 조사·조치: 이상이 있으면 현재·이전 버전과 의존성을 대조하고, 허용된 복구를 실행하거나 승인을 요청한다.
  4. 마무리: 새 표본으로 회복을 확인한다. 해결되지 않으면 시도한 내용과 필요한 결정을 담당자에게 전달한다.

사용자에게는 현재 상황 · 다음 행동 · 필요한 결정을 담은 배포 카드가 보인다. 상세 근거는 펼쳐 볼 수 있으며, 승인·거절·자동 변경 중단을 같은 흐름에서 처리한다.

에이전트가 필요한 부분

Strands 에이전트는 배포 설명·로그·검사 결과에서 가설을 세우고 다음에 확인할 도구를 선택한다. 이전 버전도 실패하면 의존성으로 조사를 옮기고, 관측이 부족하면 추가 근거를 모은다. 변경 권한과 회복 판정은 코드로 통제한다.

차별화 가설: 한 서비스의 배포 후 확인을 쉽게 맡기고, HTTP 성공 여부를 넘어 실제 기능 결과에 따라 조사·복구·인계를 끝까지 연결한다. 기존 운영 제품도 조사와 복구 기능을 제공하므로, 차이는 동일 조건의 수동 작업·고정 순서 스크립트와 비교해 입증한다.

03. 한 서비스에서 완결하는 MVP

첫 지원 범위: AWS 한 계정·한 리전의 API Gateway + Lambda 서비스 하나. 자동 변경은 미리 승인한 이전 버전으로 지정 alias를 되돌리는 작업 하나로 제한한다.

반드시 구현할 기능 완료 기준
배포 이벤트와 지속 관측 브라우저를 닫아도 시작·진행하고 상태를 다시 확인할 수 있음
Strands 조사 루프 실제 Bedrock 추론과 관측에 따른 도구 선택 기록
기능 검사와 버전 대조 같은 입력의 응답 내용·실행 버전·요청 ID·시각을 기록
승인과 제한된 롤백 서버에 승인을 저장하고 최신 alias revision이 일치할 때만 변경
회복 확인과 인계 조치 이후 새 표본으로 판정하고 미해결 이유·남은 결정을 표시

웹은 TypeScript + S3/CloudFront, 업무 API는 API Gateway/Lambda, 인증은 Cognito로 구성한다. 증거는 DynamoDB/S3에 저장하고 CDK로 환경을 재현한다. 정상 관측은 코드로 수행하며 새 이상이나 판단이 있을 때 모델을 호출한다.

신뢰할 수 있는 종료 조건

  • 회복 확인: 변경 후 수집한 서로 다른 두 검사 묶음이 통과해야 한다. 묶음당 배송비 견적 요청 5개를 검사하고 실행 버전과 시각을 남긴다. 회복 뒤에도 남은 기간을 관측한다.
  • 미검증: 표본이 없거나 근거가 충돌하면 정상으로 닫지 않는다. 재시도 후에도 확인할 수 없으면 인계한다.
  • 변경 제한: 한 배포당 자동 롤백은 최대 1회. 대상·승인·기한·revision을 실행기가 검사하며, 동시 배포나 결과 불명 시 재조회한다.

멀티클라우드, EKS, 자율 코드 수정, 임의 명령 실행은 범위에서 제외한다. Slack 알림과 이력 검색은 핵심 흐름을 완성한 뒤 추가한다.

04. 5분 안에 보여줄 세 장면

실제 AWS에 배송비 견적 API를 배포한다. 합성 입력과 통제된 결함을 사용하되 에이전트는 실제 응답·로그로 판단한다. 장애 종류와 정답은 에이전트에 제공하지 않는다.

장면 관측한 상황 에이전트의 행동
A · HTTP 200의 기능 오류 새 버전은 배송비가 틀리고 이전 버전은 같은 검사를 통과 원인 대조 → 허용된 롤백 → 새 표본으로 회복 확인
B · 롤백으로 풀리지 않는 오류 공통 의존성 문제로 현재·이전 버전 모두 실패 의존성 조사 → 불필요한 롤백 없이 근거와 함께 인계
C · 확인할 수 없는 상태 검사나 증거 수집 경로가 끊겨 표본이 없음 미검증 유지 → 제한된 재시도 → 판단 요청

데모는 검사 묶음 간격을 15초로 줄여 촬영하고 화면에 표시한다. 기본 30분 관측은 1분 주기로 별도 검증한다. 버전·요청·시각이 남은 실행 기록으로 영상과 실제 동작을 연결한다.

AWS Builder Center 글은 실제 구현·실패·사용자 검증을 소재로 최대 3편 작성한다. 규정상 편당 0.2점, 최대 0.6점 가산이며 제목에 Agents for Humans를 포함한다. 공식 규정

06. 성과는 이렇게 검증한다

기술: 네 종류의 문제, 별도로 남기는 실패

기능 회귀·공유 의존성·관측 부족·동시성/중복에서 각 6개씩 24개 사례를 준비한다. 12개는 개발에, 나머지 12개는 최종 평가에 사용한다. 최종 평가 사례를 5회씩 반복한 60회 실행은 사례 수와 구분해 보고한다.
